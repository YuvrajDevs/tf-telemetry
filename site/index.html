Turbofan Telemetry

A real-time pipeline for jet-engine sensor data. NASA's public C-MAPSS dataset (200 engines, each run until it failed) is replayed as a live fleet into Kafka, processed by Spark Structured Streaming into Delta Lake bronze / silver / gold tables, and turned into health scores and maintenance alerts that fire weeks before failure. Delivery is exactly-once, proven after a hard crash.

How data flows

Each engine is a stream of readings (21 sensors per flight cycle). The key is the engine id, so one engine's readings stay in order on one Kafka partition. Each layer is a separate streaming query with its own checkpoint, so a crash resumes exactly where each one stopped.

Bronze: never parse, so nothing is ever lost Silver: schema checks, event-time watermark, dedupe on a deterministic event id Gold: stateful health score per engine with idempotent MERGE

The bug that mattered: 44% of one fleet never alerted

The first health index was tuned on FD001, where every engine has a compressor (HPC) fault. On FD003, 44 of 100 engines have a fan fault: four sensors move the opposite way, cancelling the rising ones, so the score stayed near zero until failure. The fix scores both patterns and takes the worse one, with the fan pattern weighted 0.4 so lead times and false alarms match FD001. The weight was chosen on odd-numbered engines and confirmed on the even ones.

The same check also labels the fault: the 44 engines v1 missed are exactly the 44 v2 labels FAN, so each alert can go straight to the right maintenance team.

Reliability, proven rather than claimed

scripts/demo.sh streams the whole fleet with deliberate chaos, kills the Spark application with kill -9 mid-stream, restarts it, and compares every event in silver with the producer's manifest.

  1. Deterministic event id (uuid5 of engine + cycle): the same reading always has the same id.
  2. Checkpoints + Delta atomic commits: a micro-batch is either fully written or not at all, and replayed after a crash.
  3. Watermark dedupe in silver removes retries and producer duplicates.
  4. Idempotent MERGE in gold: replaying a batch can't move an engine backwards or raise an alert twice.
  5. Dead-letter table: one broken message never stops the stream; every bad record is kept with its reason.

Throughput and sizing

Load-tested on a laptop-class machine (4 cores, 1 Kafka broker, Spark local[*]) with scripts/loadtest.py. The stateful gold step turned out to be the bottleneck: with it switched off, the same load ran at less than half the latency, so in production it runs as its own job. Details in docs/capacity-plan.md.

Run it yourself

No accounts or cloud needed: Docker, Python 3.10–3.12 and Java 17.

python -m venv .venv && source .venv/bin/activate
pip install -r requirements.txt
docker compose up -d                 # Kafka on localhost:9092
python -m telemetry.cli download     # NASA data, ~12 MB
./scripts/demo.sh                    # chaos + crash + exactly-once check
streamlit run dashboard/app.py       # live dashboard
